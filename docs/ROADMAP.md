# 계획 보드 — 여러 단계로 나눈 일

**대화창은 사라진다. 계획은 여기 있어야 산다.**

BLOCK7 은 여러 대화창(클로드 코드 여럿 · GPT Codex)이 번갈아 작업한다.
한 창에서 "1단계 → 2단계 → 3단계" 로 계획을 세워도, 그 창을 닫으면 계획이
통째로 사라진다. 실제로 2026-09 교회 그룹 작업이 그랬다 — 1단계를 마친 창이
닫히고, 다음 창은 3·4단계가 무엇이었는지 알 길이 없었다.

## 지키는 법 — 세 줄

1. **여러 단계로 나눈 계획을 세웠으면 그 자리에서 여기 적는다.** 1단계를
   시작하기 전에 적는다. "나중에 정리하겠다" 는 곧 잊는다는 뜻이다.
2. **한 단계를 끝내면 그 줄의 상태와 근거(버전·PR)를 바로 고친다.** 배포 확인과
   같은 호흡으로 한다.
3. **묶음이 다 끝나면 여기서 지우고** 설계 배경만 `BLOCK7-작업인계.md` 로 옮긴다.
   ⚠️ 이 파일은 **짧게 유지한다.** 길어지면 아무도 안 읽는다 — 그게 정확히
   `BLOCK7-작업인계.md` 의 '5. 남아 있는 과제' 장이 67KB 가 되어 죽은 까닭이다.

## 적는 모양

묶음마다 이 셋을 적는다. **③ 이 가장 값지다** — 표는 다시 만들 수 있지만,
왜 그 길을 골랐고 무엇을 피했는지는 그 창이 닫히면 영영 사라진다.

① 단계 표 (무엇을 · 상태 · 근거)
② 다음에 잡을 것 — 조사한 것까지 함께
③ **정해 둔 것과 하지 말 것** — 까닭까지

### 7단계 — 배포가 실제로 도는 것을 확인했다 (2026-09-20)

`workflow_dispatch` 로 손수 돌려 **건너뛰지 않고 끝까지 갔다.** 단계가 전부
실행됐고(건너뛰면 0초인 '올리기' 단계가 27초), 로그 마지막 줄이
`Production deploy succeeded · sweeter7.web.app`.

⚠️ **작업 환경에서는 배포된 주소를 열어 볼 수 없다.** 이 컨테이너는 바깥
웹으로 못 나간다 — `block7.my` 도 똑같이 막힌다(막힌 것이지 죽은 것이 아니다).
그래서 **화면 확인은 언제나 HB 몫**이고, 우리가 할 수 있는 것은
①깃헙 액션 로그 ②헤드리스 크로미엄으로 `build-sweeter/` 를 직접 여는 것 둘뿐이다.

### 6단계에서 한 일

**⚠️ `sweeter.html` 을 저장소에 커밋하지 않는다.** 깃헙 페이지는 저장소의 모든
파일을 `block7.my/…` 로 내보낸다 → 커밋하면 **`block7.my/sweeter.html` 이
"같은 도메인에서 로그인이 켜진 Sweeter"** 가 되어 버린다. 바로 위 금지 조항이
말리는 그 모양이다. 그래서 산출물은 **배포할 때만** 만든다:

    tools/make-sweeter-prod.sh  →  build-sweeter/   (.gitignore 됨)
      index.html      = index.html 에서 APP_PRODUCT·제목·OG 를 바꾼 것 (DEV_MODE 는 false 그대로)
      manifest.json   = manifest-sweeter.json
      icon.png · fonts/ · firebase-messaging-sw.js

  → `index.html` 안의 `manifest.json` 링크를 **안 바꿔도 된다**. 담는 폴더가
    다르니 이름은 그대로 두고 **내용물만** Sweeter 것으로 넣는다.

**빈 기기로 로그인하면 클라우드가 어떻게 되는가** — 실제로 돌려 확인했다.
로그인 경로가 타는 길은 이렇다:

  `_localOwner()` → null (제 칸이 비었다) → `resetStateToDefaults()`
  → `_fbLoadPersistedBase()` → null (5단계에서 가른 덕) → **병합을 아예 안 한다**
  → `applyRemoteState(클라우드)` 로 통째로 받는다

즉 3자 병합이 돌지 않는다 — 사고가 날 수 있는 길로 아예 들어가지 않는다.
그 뒤 처음 저장할 때 `_psProject(ST, prior)` 가 BLOCK7 의 화면 설정을
클라우드에 **되돌려 놓는다**. (시나리오 2·3·4 가 지킨다)

**푸시는 손대지 않았다.** 새 도메인은 알림 권한이 `default` 라 **저절로 켜지지
않는다** — 코드를 고칠 까닭이 없었다. 다만 아래 '아직 안 한 것' 참고.

### 아직 안 한 것 (급하지 않음)

- **Sweeter 에서 알림을 켜면 두 앱이 같이 울린다.** 발송 서버(`versepush`)는
  클라우드의 `settings.notify` 를 보는데, 그 칸은 BLOCK7 것이다 (Sweeter 몫은
  `productSettings.sweeter` 에 들어 있어 서버가 못 본다).
  → 서버가 제품을 알아보게 만들기 전에는 **Sweeter 에서 알림을 켜지 말 것.**
- **Sweeter 전용 공유 이미지(og:image)가 없다.** 지금은 이미지 없는 카드로
  나간다 — BLOCK7 그림을 그대로 쓰면 이름과 그림이 어긋나서 뺐다.
- `sweeter.my/…` 짧은 주소(교회 그룹의 `block7.my/tlc` 같은 것) — 지금은 없다.
- 이른 부팅 키 둘(`b7v1_devw`·`b7v1_uiscale`)은 `_lsk()` 를 못 쓴다.
  `LS_KEY` 보다 **먼저 도는 script 블록**에 있기 때문. 도메인이 갈리면
  어차피 안 섞이므로 그대로 둔다.

### 4단계에서 한 일 — 2026-08-31 사고의 뿌리를 뽑았다

이름을 `_lsk(name)` **한 곳**에서 `LS_KEY + '_' + name` 으로 만든다.
제품·빌드가 갈리면 기준점도 갈린다.

| 빌드 | 저장 칸 | 기준점 |
|---|---|---|
| BLOCK7 운영본 | `b7v1` | `b7v1_syncbase` ← **예전과 한 글자도 같다** |
| BLOCK7 개발본 | `b7v1_dev` | `b7v1_dev_syncbase` |
| Sweeter 개발본 | `b7v1_sweeter_dev` | `b7v1_sweeter_dev_syncbase` |
| Sweeter 운영본 | `b7v1_sweeter` | `b7v1_sweeter_syncbase` |

가른 키는 다섯: `owner`·`syncbase`·`syncmeta`·`devid`·`conflicts`.
(`devid` 를 안 가르면 두 앱이 계정 문서의 **같은 기기 자리**에 푸시 등록을
덮어써서 한쪽을 켜면 다른 쪽 알림이 꺼진다)

**실기기가 아니라 진짜 브라우저로 돌려 확인했다** — 옛 이름으로 기준점이 이미
적힌 기기를 흉내내고 세 빌드를 열었다. 운영본은 그 값을 그대로 읽었고
(`uid-hb-1234`·`olddevice123`), Sweeter 는 눈앞에 `b7v1_owner` 가 있어도
읽지 않았다(null). 어느 빌드도 옛 칸을 건드리지 않았다.

### 5단계 — HB 가 고를 것 (조사해 둔 것)

⚠️ **깃헙 페이지는 저장소 하나에 도메인 하나만** 붙는다 (`CNAME` 에 `block7.my`).
`sweeter.my` 를 사도 지금 자리에는 못 붙는다. 둘 중 하나:

- **(가) 파이어베이스 호스팅** — 이미 쓰는 프로젝트(`block7-8f24e`), 추가 비용
  없음. **저장소 하나·파일 하나 구조가 유지된다.** ⭐ 권함.
  (지금 `firebase.json` 에 `hosting` 칸이 없다 — 더해야 한다)
- (나) 저장소를 하나 더 — 공짜지만 "한 파일에서 셋을 뽑는다" 가 갈라져서
  고칠 때마다 두 군데를 챙겨야 한다.

도메인을 안 사고 **먼저 확인만** 하려면 `sweeter.block7.my`(곁가지 주소)로도
최종 모습과 **동작이 완전히 같다** — 도메인이 갈리면 저장 칸이 갈리기 때문.

그 밖에 HB 가 클릭할 것: **Firebase 콘솔 → Authentication → 설정 →
승인된 도메인**에 새 주소 더하기. 안 하면 로그인이 막힌다.

### 정해 둔 것 · 하지 말 것

- ⚠️⚠️ **클라우드 문서를 제품별로 가르지 말 것.** 위 '최종 모양'의 첫 번째
  경우가 그것으로 무너진다. 가르는 것은 **화면 취향(`_PRODUCT_SCOPED`)과
  이 기기 전용 키(`_lsk`)뿐**이다.
- ⚠️ **BLOCK7 운영본의 키 이름은 한 글자도 바꾸지 말 것.** 바뀌는 순간 지금
  쓰는 기기가 전부 "처음 보는 기기"가 되어 기준점을 잃는다. 그래서 접두사를
  새로 짓지 않고 `LS_KEY` 를 그대로 앞에 뒀다.
- **새 저장 키를 만들 때는 고정 이름을 쓰지 말고 `_lsk()` 를 쓸 것.**
  규칙을 한 곳에 뒀으니 앞으로 만드는 키는 저절로 안전해진다.
- **`sweeter-dev.html` 의 Firebase 는 계속 꺼 둔다.** 막던 까닭은 없어졌지만,
  개발본은 `block7.my` 에 얹혀 살아 같은 도메인에 로그인 두 벌이 오간다.
  켜는 자리는 **제 도메인에 설 `sweeter.html`** 이다 (6단계).
- 1·2단계 가져오기는 **임시 다리다.** 도메인이 갈리면 브라우저 저장 칸도
  갈려서 그날로 못 쓴다 — 그때 7단계로 뗀다. 그 대신 그냥 로그인하면 된다.
