# 동기화 V2 — 감사 결과와 설계 (HB 확인용)

> ⚠️ **이 문서는 아직 "제안"이다.** 여기 적힌 것 중 코드로 옮긴 것은 **하나도 없다.**
> HB가 이 문서를 읽고 "1단계부터 해" 라고 말한 뒤에 시작한다.
> 지금 쓰는 데이터·클라우드 문서(`state`, `backup_0~2`)는 **한 글자도 건드리지 않았다.**
>
> 배경은 `BLOCK7-작업인계.md` 7장에 다 있다. 이 문서는 그 뒤를 잇는다.

---

## 0. 세 줄 요약

1. **지금 구조는 "사용자 상태 전체"를 글자 한 덩어리로 저장한다.** 그래서 두 기기가
   같은 날 같은 시간대를 각각 고치면 **한쪽 판이 통째로 이기고 다른 쪽은 사라진다.**
   이건 버그가 아니라 지금 설계가 하기로 되어 있는 일이다 (`tests/test_boot.js` 시나리오 3이
   그 손실을 **정답으로** 못 박아 두고 있다).
2. 할일에 **고유번호가 없다.** 그래서 "같은 할일"을 알아볼 방법이 없고, 병합은 늘
   배열 통째로 이길지 질지만 고를 수 있다.
3. 고치는 방향은 **항목 단위 저장 + 항목 단위 병합 + 진짜 충돌만 사람에게 묻기** 다.
   한 번에 갈아엎지 않고, 지금 것을 그대로 둔 채 **옆에 새 것을 같이 쓰다가** 옮긴다.

## 1. 지금 무엇 때문에 데이터가 사라질 수 있는가

### 1-1. 저장 단위가 너무 크다 (근본 원인)

클라우드에는 문서가 **하나뿐**이다.

```
users/{uid}/data/state = { json:"상태 전체를 글자로 만든 것", rev:정수, dev:기기ID, appVer, updatedAt }
```

병합은 그 글자를 다시 객체로 풀어서 **자료형마다 다른 규칙**으로 섞는다
(`_fbMerge` → `_mgDay` / `_mgContainerKeys` / `_mgEntryArray` / `_mgById`).

가장 아픈 자리는 `days` 다:

| 단계 | 병합 단위 |
|---|---|
| 날짜 (`2026-08-28`) | 키 단위 — 다른 날짜는 서로 안 건드린다 ✅ |
| 그 날의 `big` / `small` / `events` | 키 단위 |
| 그 안의 **구간(`am`/`pm`/`night`)** | **배열 통째로** ❌ |

즉 **같은 날 · 같은 구간**을 두 기기가 각각 고치면, `_mgWhole` 이 "둘 다 바꿨다 →
손에 든 쪽(local)" 으로 판정해 **상대 기기의 그 구간 배열 전체를 버린다.**

> 아이폰에서 '오전'에 할일 하나를 더하고, 맥에서도 '오전'에 다른 할일을 더하면
> **둘 중 하나만 남는다.** 이게 HB가 계속 겪는 그 증상이다.

### 1-2. 할일에 고유번호가 없다

할일은 `{text, done, ...}` 모양이고 **id 가 없다.** 그래서

- "아이폰이 더한 것"과 "맥이 더한 것"을 구분할 수 없다 → 합칠 수 없다.
- 할일을 다른 날·다른 구간으로 옮기면 **지우고 새로 만든 것**과 구별되지 않는다.
- "같은 할일의 제목만 바뀌었다"와 "다른 할일이다"를 구별할 수 없다.

말씀 모음(`verseCollections`)·연락처(`contacts`)에는 `id` 가 있어서 **id 단위로 잘 합쳐진다**
(`_mgById`). 즉 답은 이미 이 코드 안에 있다 — 할일에도 같은 것을 주면 된다.

### 1-3. 저장이 너무 자주, 그리고 "사람이 안 만졌는데도" 일어난다

`rawSave()` → `fbPushState()` 는 화면을 그리며 값을 다듬을 때도 불린다
(설정 기본값 채우기, 범위 가두기, 목록 다시 계산…). 7-2-4에서 한 번 크게 데어
**"사람이 만진 직후 3초 안의 저장만 편집으로 센다"** 는 가림막(`_fbIsUserEdit`)을
붙여 두었지만, **올려 보내는 것 자체는 그대로다** — 34시간에 `rev` 가 302 올라간
것이 그 증거다. 전체 상태를 300번 다시 쓰면, 그 300번마다 "통째로 이기고 지는"
판정이 다시 일어난다.

### 1-4. 커밋 도중의 편집이 덮일 수 있다

`_fbCommit()` 은 트랜잭션 안에서 `ST` 를 읽어 병합하고, 끝난 뒤
`_fbApplyStateToApp(mergedApply)` 로 그 결과를 `ST` 에 되쓴다.
그 사이(수백 ms)에 사람이 새로 친 글자는 `mergedApply` 에 없다.
`_fbDirtySeq` 가 남아 다시 커밋되긴 하지만, **그때의 `ST` 는 이미 되쓰인 뒤**라
사라진 편집이 되살아나지는 않는다.

> 지금까지 크게 보고되지 않은 것은 창이 600ms 로 짧기 때문이지, 안전해서가 아니다.
> **회귀 테스트로 못 박아야 하는 자리다** (아래 7장 목록에 넣었다).

### 1-5. `rev` 가 크다고 옳은 데이터가 아니다

`rev` 는 "몇 번째 쓰기냐" 일 뿐이다. 빈 상태로 300번 쓴 기기가 `rev` 300이다.
지금은 `_fbHasAdoptedCloud()`·`_fbBulkLoss()` 로 그 구멍을 막고 있는데,
**막는 방식이지 아는 방식이 아니다.**

### 1-6. 백업이 "누가 원본인지" 를 안 남긴다

`backup_0~2` 의 `dev` 는 **병합을 실행한 기기**다. 정작 알고 싶은
"이 내용을 만든 기기" 는 어디에도 없다.

### 1-7. 개발본으로는 확인할 수 없다

`index-dev.html` 은 Firebase 가 꺼져 있다. 즉 **다기기 동기화는 개발본에서 한 번도
시험된 적이 없다.** 지금까지 모든 동기화 수정은 운영에 올린 뒤 HB의 실기기에서
검증됐다 — 사고가 반복된 진짜 이유 중 하나다. (→ 6장 스테이징 제안)

## 2. ST 의 칸을 세 가지로 나눈 표 (⚠️ HB 확인이 필요한 부분)

V2 로 옮기기 전에 **어떤 칸이 어디에 속하는지** 부터 정해야 한다.
아래가 제안이다. **틀린 줄이 있으면 그 줄만 말해 주면 된다.**

### (가) 계정 전체에서 공유 — 모든 기기가 같아야 하는 것

| 칸 | 무엇 |
|---|---|
| `days` | 할일·스몰블럭·일정 (**V2에서 항목 단위로 쪼갠다**) |
| `memorizationLog` | 암송 기록 |
| `verseLikeLog` `verseShareLog` `verseDeeperLog` `verseEvenDeeperLog` | 말씀 반응 기록 |
| `verseCollections` | 말씀 모음 (이미 id 있음) |
| `contacts` | 연락처 (이미 id 있음) |
| `secs` `secArchive` | 시간 구간 정의 |
| `vis` `prevVis` `preset` | 어떤 구간을 보여줄지 |
| `settings` 의 대부분 (아래 (나)·(다) 제외 전부) | 할일 규칙·말씀 표시 규칙·공유 설정 등 |
| `productSettings` | 다른 제품(Sweeter) 몫 보관함 — **절대 지우지 말 것** |

### (나) 기기별로만 — 클라우드에 올리지 않는 것

| 지금 어디 | 무엇 | 비고 |
|---|---|---|
| `b7v1_uiscale` | 화면 크기 배율 | 이미 기기별 ✅ |
| `b7v1_devw` | 기기 폭 | 이미 기기별 ✅ |
| `b7v1_layform` | 폰/와이드 배치 | 이미 기기별 ✅ |
| `b7v1_devid` | 기기 고유번호 | 이미 기기별 ✅ |
| `b7v1_owner` | 이 기기 로컬이 어느 계정 것인지 | 이미 기기별 ✅ |
| `b7v1_syncbase` `b7v1_syncmeta` | 병합 기준점 | 이미 기기별 ✅ |
| `b7v1_notiflog` `b7v1_notifintent` | 알림 진단·클릭 의도 | 이미 기기별 ✅ |
| `b7_devNotesRead` `b7_devNotesTrash` | 개발자 쪽지 로컬 표시 | 이미 기기별 ✅ |
| **(제안) `settings.notify` · `settings.verseAlarm` 의 켜기/끄기** | 알림 스위치 | ⚠️ **지금은 계정 공유라 한 기기에서 끄면 전부 꺼진다.** 인계문서에도 "기기별 UI 없음" 으로 남아 있다. V2 에서 `devices/{deviceId}` 로 옮길지 **HB 결정 필요** |

> ⚠️ `_PRODUCT_SCOPED` (제품별 설정)는 **기기별과 다른 이야기**다. 그건 BLOCK7 과 Sweeter 를
> 가르는 것이고, 여기 (나)는 아이폰과 맥을 가르는 것이다. 둘을 섞지 말 것.

### (다) 아예 동기화할 필요가 없는 것 (지금 화면·지금 고른 자리)

| 칸 | 왜 |
|---|---|
| `settings.verseCurrentIdx` | **지금 보고 있는 말씀 번호.** 이것이 동기화되기 때문에 예전에 알림으로 연 말씀이 다른 기기 값으로 되돌아갔다 (그래서 `_vfOverrideVerse` 라는 우회로가 생겼다) |
| `settings.verseLastShownDate` | 오늘 말씀을 이미 보여줬는지 — 기기마다 다르다 |
| `collapsed` | 어느 구간을 접어 뒀는가 — 화면 상태 |
| `settings.wmViewMode` 등 "지금 어느 탭" 류 | 화면 상태 |

> ⚠️ (다)로 옮기는 것은 **동작이 바뀌는 변경**이다. 예를 들어 `verseCurrentIdx` 를
> 동기화에서 빼면 "맥에서 넘긴 말씀이 아이폰에도 그대로 보이는" 지금 동작이 사라진다.
> HB가 그 동작을 원하는지 **먼저 확인해야 한다.**

## 3. Sync V2 데이터 모델 (제안)

### 3-1. 문서 구조

```
users/{uid}/v2/meta/main                     — 스키마 버전 · 마지막 마이그레이션 · 항목 수 요약
users/{uid}/v2/items/{itemId}                — 할일 · 스몰블럭 · 일정
users/{uid}/v2/settings/{groupId}            — 설정을 충돌 범위별로 쪼갠 것
users/{uid}/v2/verseCollections/{collectionId}
users/{uid}/v2/verseCollections/{collectionId}/verses/{verseId}
users/{uid}/v2/contacts/{contactId}
users/{uid}/v2/logEvents/{eventId}           — 좋아요 · 암송 · 공유 · Deeper
users/{uid}/v2/conflicts/{conflictId}        — 사람이 골라야 하는 것만
users/{uid}/v2/devices/{deviceId}            — 기기 이름 · 마지막 접속 · 기기 전용 설정
```

> **원안(`users/{uid}/data/v2/items/...`)과 다른 점 하나.** Firestore 에서
> `data` 는 이미 **문서**다(`data/state`). 그 아래에 다시 컬렉션을 매달면
> 기존 `state` 문서와 같은 이름 공간을 나눠 쓰게 되어 보안 규칙이 헷갈린다.
> `users/{uid}/v2/...` 로 **완전히 떼어 놓으면** 규칙을 "V1 은 이 규칙, V2 는 저 규칙"
> 으로 깔끔히 가를 수 있고, 되돌릴 때도 V2 컬렉션만 무시하면 끝난다.
> (그 외에는 원안과 같다.)

### 3-2. 항목(item) 문서

```js
{
  id: "it_8f3a…",          // 한 번 정해지면 절대 안 바뀐다
  kind: "big" | "small" | "event",
  dateKey: "2026-08-28",   // 옮기면 이 값만 바뀐다 (id 는 그대로)
  secId: "am",
  rank: 1500,              // 순서 (사이 값을 낼 수 있게 띄엄띄엄)
  text: "설교 준비",
  done: false,
  star: false, …           // 그 밖의 칸은 지금 쓰는 것 그대로

  version: 7,              // 이 항목이 몇 번 바뀌었나 (문서 전체 rev 아님)
  updatedAt: <서버시각>,
  updatedByDevice: "dev_…",
  deletedAt: null          // 지우면 시각을 적는다 (tombstone)
}
```

**핵심 세 가지**

1. **`id` 는 영원하다.** 날짜·구간을 옮겨도 유지된다 → "옮김"과 "지우고 새로 만듦"이
   구별된다.
2. **`version` 은 항목마다 따로 센다.** 전체 문서의 `rev` 하나로 온 세상을 판정하던
   것을 그만둔다.
3. **삭제는 즉시 소멸이 아니라 `deletedAt` 표시**다. 그래야 "지운 것"과 "아직 못 받은 것"이
   구별된다. (지금 구조에서 반복된 사고의 절반이 이 구별이 안 돼서 났다)

**순서(`rank`)** — 지금은 배열의 자리가 곧 순서라 배열을 통째로 다뤄야 했다.
띄엄띄엄한 숫자를 주면 사이에 끼워 넣기가 다른 기기와 부딪히지 않는다.
두 기기가 같은 자리에 넣어 숫자가 같아지면 `id` 로 순서를 정한다(어느 기기에서 보나 같은 결과).

### 3-3. 설정을 쪼개는 기준 (`settings/{groupId}`)

지금 `settings` 는 칸이 **115개**다. 한 덩어리로 두면 "글자 크기 바꿨는데 알림 설정이
되돌아갔다" 가 계속 난다. 부딪히는 범위대로 나눈다:

| groupId | 담는 것 |
|---|---|
| `todo` | `autoCarryOver` `dayStartHour` `bigLimit` `smallLimit` `carry*` `showSmallBlocks` … |
| `view` | `theme` `themePresetId` `dowFormat` `sundayRed` `show*Btn` `monthTitle*` `loopViews` … |
| `verse` | `verseBar*` `verseMode` `verseSneak*` `verseFull*` `verseCount*` `vg*Exclude*` … |
| `verseFull` | `vfThemes` `vfThemeBySec` `vfTextScale` `vfArt*` `vfCycleMode` `hi*` `imgHi` … |
| `share` | `imgIncl*` `txtIncl*` `txtRef*` `shareSize*` |
| `widget` | `verseWidget*` `verseCards` `verseCard*` |
| `notify` | `notify` `verseAlarm` (⚠️ 2장 (나) 결정에 따라 기기별로 갈 수도 있음) |
| `layout` | `layout.cols` 등 위젯 배치 |
| `uiLevel` | `uiLevel` `verseUiLevel` `uiLevelIconSet` |

한 칸을 고치면 그 그룹 문서 하나만 쓴다 → 다른 그룹과 절대 부딪히지 않는다.

### 3-4. 로그(`logEvents`)

좋아요·암송·공유·Deeper 는 **더해지기만 하는 기록**이다. 지금도 합집합이라 잘 돌지만,
`eventId` 를 주면 "같은 것을 두 번 세는" 문제까지 사라진다.
`eventId = 해시(kind + ref + time + deviceId)` 로 만들면 **여러 번 올려도 한 번만 들어간다.**

### 3-5. 화면 그리기는 절대 operation 을 만들지 않는다

지금의 `_fbIsUserEdit()`(3초 가림막)은 **증상 가림막**이다. V2 에서는 아예
**사람의 동작에서만** operation 을 만든다. 값 다듬기·기본값 채우기·목록 재계산은
`origin:'normalization'` 으로 로컬에만 남고 **클라우드로 올라가지 않는다.**
(올릴 필요가 있으면 다음 사람 동작에 묻어 올라간다)

## 4. 로컬 outbox (IndexedDB)

사람이 편집하면 **화면만 바꾸고 끝내지 않는다.** 먼저 operation 을 IndexedDB 에 적는다.

```js
{ opId, deviceId, entityType, entityId, baseVersion, fields:{…},
  createdAt, origin:'user'|'normalization'|'migration', retry:{n, nextAt, lastError} }
```

- 앱을 껐다 켜도 · 아이폰이 백그라운드로 밀어내도 · 오프라인이어도 **남는다.**
- 시작 · `online` · `focus` · `pageshow` 때 다시 보낸다.
- **서버가 받았다고 확인한 뒤에만** outbox 에서 지운다.
- 같은 `opId` 를 다시 보내도 **한 번만** 적용된다 (`meta/main.appliedOps` 또는 항목의
  `lastOpId` 로 판정).

> ⚠️ Firestore 트랜잭션은 오프라인에서 즉시 실패하고, 온라인이어도 **여러 번 재실행될 수
> 있다.** 그래서 **트랜잭션 함수 안에서는 `ST` 도 화면도 절대 건드리지 않는다.**
> (지금 `_fbCommit` 은 트랜잭션 밖에서 `mergedApply` 를 적용하므로 이 규칙은 지켜지고 있다.
> V2 에서도 깨지 말 것)

## 5. 충돌은 언제 사람에게 묻는가

**대부분은 안 묻는다.** 자동으로 합친다:

| 상황 | 처리 |
|---|---|
| 서로 **다른 항목**을 고쳤다 | 충돌 아님 — 둘 다 산다 |
| **같은 항목의 다른 칸**을 고쳤다 (한쪽은 제목, 한쪽은 완료) | 칸 단위로 합친다 |
| 한쪽만 고쳤다 | 고친 쪽 |
| 로그가 양쪽에 쌓였다 | 합집합 |

**이때만 묻는다:**

1. **같은 항목의 같은 칸**을 서로 다르게 고쳤다
2. 한쪽은 **지웠고** 한쪽은 **고쳤다**
3. 순서 변경이 서로 부딪혀 자동으로 정할 수 없다
4. 합친 결과에서 **항목이 대량으로 사라진다** (지금의 `_fbBulkLoss` 를 이어받는다)
5. **낮은 버전이나 정체를 알 수 없는 기기**가 구조를 줄였다
6. **커밋 도중 생긴 새 편집**과 커밋 결과가 겹친다

### 5-1. 물을 때까지는 "격리" 한다

충돌이 나면 **어느 쪽도 지우지 않는다.** `conflicts/{conflictId}` 에 세 벌
(base / local / remote)을 통째로 넣고, **그 항목만** 쓰기를 멈춘다.
나머지 항목은 평소처럼 계속 동기화된다.

```js
{ conflictId, entityType, entityId,
  base:{…}, local:{…}, remote:{…},
  localDeviceId, remoteDeviceId, localDeviceLabel, remoteDeviceLabel,
  appVersion, baseVersion, localVersion, remoteVersion,
  clientEditedAt, serverObservedAt,
  summary:{added, changed, removed},
  choice:null, resolvedAt:null,
  restore:{…}                    // 되돌리기용 원본
}
```

### 5-2. "동기화 충돌 해결" 화면

- **기기를 바꿨다는 이유만으로는 절대 안 뜬다.** 진짜 못 정하는 것이 있을 때만 뜬다.
- 전체 A/B 중 고르라고 하지 않는다. **항목·칸 단위**로 보여준다.
- 기본 선택지:
  1. **양쪽 변경 합치기 (권장)**
  2. 충돌 항목만 직접 확인
  3. 이 기기 변경 사용
  4. 다른 기기 변경 사용
  5. 나중에 결정
- "나중에 결정"을 골라도 **아무것도 사라지지 않는다** — 격리 상태가 유지될 뿐이다.

### 5-3. 기기가 놀고 있는지(`_fbDeviceIdle`)는 참고만 한다

지금은 그것이 **데이터의 승패를 정한다.** V2 에서는 자동 합치기가 안 되는
아주 좁은 경우에 **정렬 힌트**로만 쓰고, 그것만으로 사람 데이터를 버리지 않는다.

## 6. 어떻게 옮기는가 (한 번에 갈아엎지 않는다)

| 단계 | 무엇 | 되돌리는 법 |
|---|---|---|
| **A** | 지금 `state`·`backup_0~2` 를 손대지 않고 **그대로 둔 채**, 항목 수·체크섬을 `v2/meta/main` 에 기록만 한다 | V2 컬렉션 지우면 끝 |
| **B** | 기존 할일·일정·로그에 **고유번호를 붙이는 마이그레이션** + 테스트. 여러 번 돌려도 같은 결과(idempotent) | id 는 새 칸이라 옛 코드가 무시한다 |
| **C** | **V1 이 계속 기준.** 쓰기만 V2 에도 함께 한다 (shadow write) | V2 쓰기만 끄면 끝 |
| **D** | V1 과 V2 를 자동 비교해 **빠진 것·중복**을 보고 (기기에서 눈으로 확인) | — |
| **E** | HB의 아이폰·맥에서 확인한 뒤 **읽기 기준을 V2 로** 옮긴다 | 한 줄(`SYNC_READ='v1'`)로 되돌린다 |
| **F** | 얼마간 **V1 호환 스냅샷**을 계속 남긴다 (옛 탭이 열려도 안 깨지게) | 그 스냅샷으로 즉시 복귀 |
| **G** | 마지막에 **옛 클라이언트의 V1 쓰기를 Firestore 규칙으로 막고** 새로고침 안내 | 규칙 한 줄 되돌리기 |

**마이그레이션은 반드시 idempotent** — 같은 항목에 두 번 id 를 붙이지 않는다.
`(dateKey, kind, secId, 배열 자리, text)` 로 지문을 만들어, 이미 id 가 있으면 건너뛴다.

## 8. Firestore 규칙 초안

> ⚠️ **`devNotes` 규칙은 지금 것이 더 안전하다. 이 초안에도 손대지 않고 그대로 둔다.**
> 아래는 **V2 컬렉션을 더하는 부분만** 이다. 지금 규칙에 이어 붙인다.

```
rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {

    // ── 지금 것 (그대로 둔다) ──────────────────────────────
    //  users/{uid}/data/{doc}   ← state · backup_0~2
    //  users/{uid}/pushTokens/{tok}
    //  devNotes …               ← ⚠️ 절대 건드리지 말 것
    //  verseStats …

    // ── V2 (새로 더하는 부분) ─────────────────────────────
    match /users/{uid}/v2/{document=**} {
      allow read: if request.auth != null && request.auth.uid == uid;
      allow write: if request.auth != null && request.auth.uid == uid;
    }

    // G 단계(마지막 전환)에서만 켠다 — 옛 클라이언트의 V1 쓰기를 막는다.
    // ⚠️ 이 줄을 켜기 전에 반드시 모든 기기를 새로고침해야 한다.
    // match /users/{uid}/data/state {
    //   allow read: if request.auth != null && request.auth.uid == uid;
    //   allow write: if request.auth != null && request.auth.uid == uid
    //                && request.resource.data.schema == 2;
    // }
  }
}
```

**왜 V2 는 이렇게 헐렁한가** — 항목 문서마다 조건을 걸면(예: `version` 이 반드시 커야 한다)
오프라인에서 밀린 outbox 가 통째로 막힌다. 데이터를 지키는 일은 **클라이언트의 병합 규칙**과
**tombstone** 이 하고, 규칙은 "남의 계정에 못 쓴다" 만 지킨다. G 단계에서만 스키마 조건을 건다.

## 10. 예상 위험과 대비

|---|---|---|

## 11. 되돌리는 법 (각 단계마다)

- **A~D 단계**: `users/{uid}/v2/` 컬렉션을 지우면 끝. 운영 데이터(`state`)는 손대지 않았다.
- **E 단계**: 코드의 읽기 기준 한 줄을 `v1` 로 되돌리고 배포. 그 사이 V2 에만 쌓인 변경은
  F 단계의 V1 호환 스냅샷에 이미 반영돼 있다.
- **F~G 단계**: Firestore 규칙에서 스키마 조건 줄을 지운다(주석 처리).
- **어느 단계든 최후의 수단**: 계정 탭 → 데이터 복구 → **자동 백업 보기** 로
  `backup_0~2` 시점으로 되돌린다 (지금과 똑같이 동작한다).
